# Решения и допущения

## Где ТЗ допускает разные толкования — что я выбрал

1. **Значения статусов** хранятся как enum в базе с русскими названиями из ТЗ
   («Новая», «В работе»…): база, API и интерфейс говорят одинаково, статус виден
   без преобразований.
2. **Комментарий** при возврате на доработку хранится в истории статусов
   (отдельного поля комментария у задачи по ТЗ нет). Обязательность комментария
   проверяется в базе — переход «На проверке → На доработке» без него отклоняется.
3. **Назначение исполнителя** — обязательное поле при создании задачи. Постановщик
   может переназначить исполнителя позже через «Изменить» в карточке задачи
   (в любом статусе).
4. **Смена статуса идёт только через RPC `transition_task`.** Прямое изменение
   поля `status` через API запрещено триггером даже постановщику. Это строже ТЗ
   («запрещённые переходы не пройдут»), но делает поведение предсказуемым: одна
   точка входа, одна проверка, история всегда записана.
5. **Удаление объекта** каскадно удаляет его задачи и их историю (право удаления
   у постановщика есть по ТЗ). В продакшене можно заменить на запрет удаления
   непустых объектов.
6. **Роли** хранятся в таблице `profiles` (а не в JWT-claims): роль легко сменить
   вручную в панели Supabase, и RLS всё равно проверяет её на стороне базы.
   Профиль создаётся автоматически триггером при создании пользователя; роль по
   умолчанию — исполнитель, постановщику роль назначает seed-скрипт.
7. **Список сотрудников** (имена, email, роль) виден всем вошедшим: он нужен для
   отображения автора/исполнителя в карточках и для выбора исполнителя. Если email
   сотрудников считать чувствительными, политику SELECT на `profiles` можно сузить.
8. **«Мои задачи»** есть только у исполнителя (как в ТЗ). Руководитель видит все
   задачи через карточки объектов.
9. **Задача без исполнителя** может существовать (если исполнителя сняли с задачи):
   двигаться по статусам она не может, пока не назначен новый исполнитель.
10. **Исполнитель видит объект**, где у него есть хотя бы одна задача, — в том
    числе когда все его задачи там уже приняты (доступ не «испаряется»).
11. **Счётчик задач** в списке объектов для исполнителя считает его собственные
    задачи на объекте (RLS), для постановщика — все.

## Что не успело / что можно улучшить

- Уведомления (email или realtime) о новых задачах и возвратах на доработку.
- Комментарии к задаче вне смены статуса; вложения/фото.
- Список «Все задачи» для постановщика с фильтрами по статусу/объекту/исполнителю.
- Автотесты: RLS-политики хорошо закрываются pgTAP, UI — e2e (Playwright).
- Пагинация и поиск по спискам (сейчас таблицы без пагинации на больших объёмах).
- Роль в JWT (`app_metadata`) вместо таблицы профилей — чуть быстрее политики.
- История редактирования полей задачи (сейчас в журнале только смены статусов).
- Разбиение бандла на чанки (предупреждение Vite про 500 КБ из-за Ant Design).

## Вопросы, которые уточнил бы у заказчика

- Можно ли постановщику редактировать/удалять задачу после статуса «Принята»?
  Сейчас — да.
- Нужна ли история правок полей (название/описание/исполнитель), или только статусы?
- Нужен ли комментарий при принятии задачи (сейчас — нет)?
- Может ли один человек быть и постановщиком, и исполнителем? Сейчас роль одна.
